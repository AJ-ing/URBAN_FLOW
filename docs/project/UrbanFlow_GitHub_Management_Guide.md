## 🌿 PART 2: BRANCHING STRATEGY

### Git Flow for UrbanFlow

```
main (protected)
  ├── develop (protected)
  │   ├── feature/pod1-vehicle-engine          (SAI TARUN)
  │   ├── feature/pod1-intersection-logic      (DAKSH)
  │   ├── feature/pod1-config-parser           (ISHANI)
  │   ├── feature/pod2-fixed-controller        (LAURAL)
  │   ├── feature/pod2-adaptive-controller     (DEV)
  │   ├── feature/pod3-metrics                 (PRANAV)
  │   ├── feature/pod3-exporters               (SHIKHAR)
  │   ├── feature/pod4-visualization           (RUSHIL)
  │   ├── feature/pod5-testing                 (MEDHANSH)
  │   └── feature/integration                  (AAYUSH - cross-pod)
  │
  ├── release/phase-1
  ├── release/phase-2
  ├── release/phase-3
  ├── release/phase-4
  └── release/phase-5
```

### Branch Naming Convention

**Feature Branches:**
```
feature/pod{N}-{component}-{description}

Examples:
- feature/pod1-vehicle-movement
- feature/pod2-adaptive-rules
- feature/pod3-csv-export
- feature/pod4-dashboard-ui
- feature/pod5-integration-tests
```

**Bug Fixes:**
```
bugfix/{issue-number}-{description}

Examples:
- bugfix/42-collision-detection
- bugfix/38-metrics-accuracy
```

**Hotfixes (for main):**
```
hotfix/{version}-{critical-issue}

Example:
- hotfix/1.0.1-crash-on-startup
```

**Release Branches:**
```
release/phase-{N}

Examples:
- release/phase-1
- release/phase-2
```

## 👥 PART 3: TEAM COLLABORATION WORKFLOW

### Daily Workflow for Team Members

#### **Step 1: Start Your Day (Every Morning)**

```bash
# 1. Switch to develop branch
git checkout develop

# 2. Pull latest changes
git pull origin develop

# 3. Create/switch to your feature branch
git checkout -b feature/pod1-vehicle-engine
# OR if branch exists:
git checkout feature/pod1-vehicle-engine

# 4. Merge latest develop into your branch (stay updated)
git merge develop

# 5. Resolve any conflicts immediately
# (Don't let your branch drift too far from develop)
```

#### **Step 2: Work on Your Tasks**

```bash
# 1. Make changes to your files
# 2. Test locally
python -m pytest tests/unit/test_vehicle.py

# 3. Check code quality
black src/simulation/vehicle.py
pylint src/simulation/vehicle.py

# 4. Add changes
git add src/simulation/vehicle.py

# 5. Commit with descriptive message
git commit -m "feat(vehicle): implement basic movement logic

- Add Vehicle class with position and velocity
- Implement lane-following algorithm
- Add unit tests for movement calculations
- Refs #12"

# 6. Push to remote
git push origin feature/pod1-vehicle-engine
```

#### **Step 3: Create Pull Request**

**When to Create PR:**
- Feature is complete and tested
- Code passes all local tests
- You've merged latest `develop` into your branch
- Ready for team review

**Pull Request Title Format:**
```
[POD-N] Component: Brief description

Examples:
[POD-1] Vehicle: Implement movement engine
[POD-2] Adaptive: Add queue-based decision rules
[POD-3] Metrics: Calculate throughput and wait times
```

**Pull Request Description Template:**
```markdown
## Description
Brief summary of changes

## Changes Made
- Added Vehicle class with movement logic
- Implemented collision detection
- Created unit tests with 85% coverage

## Testing Done
- [x] Unit tests pass locally
- [x] Integration tests pass
- [x] Manual testing completed

## Related Issues
Closes #12
Refs #15

## Screenshots (if UI changes)
[Attach screenshots]

## Checklist
- [x] Code follows PEP 8 style guide
- [x] Added/updated docstrings
- [x] Added/updated tests
- [x] Documentation updated
- [x] No merge conflicts with develop
```

#### **Step 4: Code Review Process**

**Reviewers (Auto-assigned via CODEOWNERS):**
- Pod Lead reviews their pod members' code
- Project Lead (Aayush) reviews cross-pod integrations
- QA Lead (Medhansh) reviews all PRs for testing

**Review Checklist:**
```markdown
- [ ] Code is clean and follows PEP 8
- [ ] Docstrings are present and clear
- [ ] Unit tests cover new functionality
- [ ] No obvious bugs or performance issues
- [ ] Meets functional requirements
- [ ] Doesn't break existing functionality
```

**Approval Rules:**
- At least 1 approval from pod lead or project lead
- All CI checks must pass (tests, linting, coverage)
- No unresolved review comments

#### **Step 5: Merge to Develop**

```bash
# After PR approval:
# 1. Merge via GitHub UI (use "Squash and Merge" for clean history)
# 2. Delete feature branch after merge

# 3. Update your local develop
git checkout develop
git pull origin develop

# 4. Start next feature
git checkout -b feature/pod1-arrival-generator
```

## 🤖 PART 5: CI/CD PIPELINE SETUP

### GitHub Actions Workflow Files

#### **File: `.github/workflows/ci.yml`**

```yaml
name: UrbanFlow CI

on:
  push:
    branches: [ develop, main ]
  pull_request:
    branches: [ develop, main ]

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        python-version: [3.8, 3.9, 3.10]

    steps:
    - uses: actions/checkout@v3
    
    - name: Set up Python ${{ matrix.python-version }}
      uses: actions/setup-python@v4
      with:
        python-version: ${{ matrix.python-version }}
    
    - name: Install dependencies
      run: |
        python -m pip install --upgrade pip
        pip install -r requirements.txt
        pip install -r requirements-dev.txt
    
    - name: Run tests with pytest
      run: |
        pytest tests/ --cov=src --cov-report=xml --cov-report=html
    
    - name: Upload coverage to Codecov
      uses: codecov/codecov-action@v3
      with:
        file: ./coverage.xml
        flags: unittests
        name: codecov-umbrella
        fail_ci_if_error: true
    
    - name: Check coverage threshold
      run: |
        coverage report --fail-under=80
```

#### **File: `.github/workflows/code-quality.yml`**

```yaml
name: Code Quality

on:
  pull_request:
    branches: [ develop, main ]

jobs:
  lint:
    runs-on: ubuntu-latest
    
    steps:
    - uses: actions/checkout@v3
    
    - name: Set up Python
      uses: actions/setup-python@v4
      with:
        python-version: '3.10'
    
    - name: Install linting tools
      run: |
        pip install black pylint flake8
    
    - name: Check code formatting with Black
      run: |
        black --check src/ tests/
    
    - name: Lint with pylint
      run: |
        pylint src/ --fail-under=8.0
    
    - name: Lint with flake8
      run: |
        flake8 src/ tests/ --max-line-length=100 --ignore=E203,W503
```

## 🔧 PART 11: CONFLICT RESOLUTION

### Common Merge Conflicts & Solutions

#### **Scenario 1: Two people edit the same file**

```bash
# Example: SAI TARUN and DAKSH both edit queue_manager.py

# DAKSH's approach:
1. Coordinate on Slack BEFORE editing shared files
2. If conflict occurs:
   git checkout feature/pod1-queue-manager-daksh
   git merge develop  # Get latest changes
   # Resolve conflicts in VSCode
   git add queue_manager.py
   git commit -m "merge: resolve conflict in queue_manager"
   git push
```

#### **Scenario 2: API interface changes**

```bash
# LAURAL changes base_controller.py interface
# DEV's adaptive_controller.py breaks

# Solution:
1. LAURAL announces interface change in #integration Slack
2. LAURAL updates interface documentation
3. DEV pulls latest develop
4. DEV updates adaptive_controller.py to match new interface
5. Integration tests verify compatibility
```

### Conflict Prevention Strategies

1. **Communicate Early:** Announce changes to shared files
2. **Small PRs:** Keep PRs < 300 lines for easy review
3. **Frequent Merges:** Merge develop into feature branch daily
4. **API Contracts:** Lock interfaces early, avoid changes
5. **Code Reviews:** Catch conflicts before merge

## 🎓 BEST PRACTICES SUMMARY

### DO's ✅

1. **Commit Often:** Small, focused commits
2. **Pull Daily:** Stay updated with develop
3. **Write Tests:** Before creating PR
4. **Review Quickly:** PRs reviewed within 24 hours
5. **Communicate:** Over-communicate rather than under
6. **Document:** Docstrings, comments, READMEs
7. **Use Issues:** Track all work via GitHub Issues
8. **Tag Commits:** Reference issue numbers in commits

### DON'Ts ❌

1. **Don't Force Push:** To develop or main (ever!)
2. **Don't Commit Secrets:** API keys, passwords, credentials
3. **Don't Ignore CI:** Fix failing tests immediately
4. **Don't Bypass Reviews:** All code must be reviewed
5. **Don't Work in Isolation:** Sync with team regularly
6. **Don't Merge Conflicts:** Communicate before editing shared files
7. **Don't Skip Documentation:** Code without docs is incomplete
8. **Don't Procrastinate Reviews:** Review PRs promptly
